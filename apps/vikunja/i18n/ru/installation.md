## Требования и подготовка

Нужны 64-разрядные Ubuntu 22.04+ или Debian 12+, Docker Engine и Compose v2.24+. Ориентируйтесь на одно ядро CPU, минимум 1 ГБ RAM (рекомендовано 2 ГБ), 5 ГБ диска плюс вложения. Образы поддерживают amd64 и arm64; рецепт проверен на amd64.

```bash
mkdir -p ~/services/vikunja
cd ~/services/vikunja
# Скопируйте файлы рецепта, включая backup.sh, restore.sh и proxy/.
cp .env.example .env
chmod 600 .env
# Два независимых значения: секрет сервиса и пароль базы.
openssl rand -hex 32
openssl rand -hex 32
```

До запуска заполните `.env`. Все параметры:

| Параметр | Назначение |
| --- | --- |
| `VIKUNJA_VERSION` | Точная версия приложения, изначально `2.7.1`. В Docker-теге префикс `v` не нужен. |
| `VIKUNJA_PORT` | Порт хоста на loopback, по умолчанию `3456`. |
| `VIKUNJA_PUBLIC_URL` | Точный адрес браузера со схемой, нестандартным портом и завершающим слешем. По умолчанию `http://localhost:3456/`; за прокси задайте внешний HTTPS URL. |
| `VIKUNJA_SECRET` | Случайный секрет сервиса, созданный выше; сохраняйте при перезапусках и восстановлении. |
| `VIKUNJA_DB_PASSWORD` | Другой случайный пароль PostgreSQL; замените заглушку до инициализации. |
| `VIKUNJA_DATA_VOLUME` | Том приложения с загруженными файлами в `/data/files`. |
| `VIKUNJA_DB_VOLUME` | Том PostgreSQL 18 в `/var/lib/postgresql`, включая версионный каталог данных. |
| `TZ` | Часовой пояс IANA, по умолчанию `Etc/UTC`. Часовой пояс аккаунта задаётся отдельно в приложении. |
| `VIKUNJA_BACKUP_DIR` | Необязательный абсолютный каталог копий; по умолчанию `backups/` рядом с рецептом. |

Скрипты загружают активный `.env` как доверенную конфигурацию shell. Защищайте файл и используйте простые сгенерированные значения. Смена пароля БД в `.env` не меняет пароль уже созданной роли PostgreSQL.

## Запуск и создание аккаунта

```bash
docker compose config --quiet
docker compose pull
docker compose up -d --wait --wait-timeout 300
curl --fail http://127.0.0.1:3456/health
# Укажите свои имя пользователя и email; пароль CLI запросит отдельно.
docker compose exec vikunja /app/vikunja/vikunja user create \
  --username=alex --email=you@example.com
```

Начального аккаунта с общим паролем нет. Откройте точный `VIKUNJA_PUBLIC_URL` и войдите с созданными данными. Регистрация выключена; дополнительные аккаунты создаются той же командой CLI. Выберите язык и часовой пояс в настройках, при необходимости подключите TOTP. Платная веб-панель администрирования Pro для этих действий не нужна. SMTP и внешний провайдер идентификации не настроены.

Контейнер `permissions` завершается успешно после назначения владельца тома `1000:1000` — это нормально. Корневая файловая система приложения доступна только для чтения; запись разрешена в `/data` для вложений и в `/tmp` для временных файлов.

## VPS

<!-- coverage:deployment-vps -->

Оставьте 3456 на loopback, PostgreSQL не публикуйте. Направьте домен на хост, задайте `VIKUNJA_PUBLIC_URL=https://tasks.example.com/`, настройте HTTPS-прокси и разрешите в firewall только SSH/HTTP/HTTPS. Храните зашифрованные копии вне сервера. Регистрация отключена, но каждому аккаунту всё равно нужны уникальный пароль и аккуратные права общего доступа к проектам.

## Доверенная локальная сеть

<!-- coverage:deployment-lan -->

Для личного доступа используйте `ssh -L 3456:127.0.0.1:3456 user@server` и `http://localhost:3456/` с соответствующим публичным URL. Для совместной работы поставьте HTTPS-прокси или привяжите порт к конкретному частному IP с ограничением firewall. PostgreSQL оставьте закрытой. Публичный URL должен совпадать с адресом, которым реально пользуются клиенты.

## Домен и HTTPS

<!-- coverage:deployment-domain-https -->

Выберите файл из `proxy/`. Caddy получает сертификаты сам, Nginx ожидает готовые файлы, Traefik — entry point `websecure` и resolver `letsencrypt`. Примеры работают на хосте и проксируют на `127.0.0.1:3456`. Контейнерному прокси нужны общая сеть и внутренний порт приложения 3456.

Задайте внешний HTTPS URL с завершающим слешем в `.env`; после смены адреса выполните `docker compose up -d --wait --wait-timeout 300`. Nginx разрешает запросы до 50 МБ, но штатный лимит файла Vikunja — 20 МБ: действуют оба ограничения. OIDC и настольные клиенты должны обращаться по тому же доступному URL приложения.

## Резервная копия

<!-- coverage:backup -->

```bash
./backup.sh
```

Скрипт останавливает Vikunja, снимает дамп PostgreSQL и собирает том приложения, `.env` и Compose в один приватный `backups/vikunja-<timestamp>.tar`. Работавшее приложение запускается снова, остановленное остаётся остановленным. PostgreSQL продолжает работать. База и вложения соответствуют одному остановленному состоянию. Зашифруйте весь архив и перенесите вне сервера: внутри реквизиты и личные данные. Один дамп базы не восстановит содержимое файлов.

## Восстановление

<!-- coverage:restore -->

**Восстановление заменяет схему public в базе и том приложения.** Используйте только свои доверенные архивы и совместимые версии приложения и БД. Вручную сравните архивный `configuration.env` с `.env`, сохранив исходный секрет сервиса; скрипт не активирует архивную конфигурацию.

```bash
# На новом хосте сначала инициализируйте соответствующий рецепт.
docker compose up -d --wait --wait-timeout 300
./restore.sh ./backups/vikunja-TIMESTAMP.tar
curl --fail http://127.0.0.1:3456/health
docker compose logs --tail=100 vikunja database
```

До замены скрипт проверяет архив и делает страховочную копию. При ошибке замены приложение остаётся остановленным; исправьте причину или повторите восстановление до запуска. После входа откройте задачу и скачайте вложение. Smoke-тест на amd64 проверяет этот путь с настоящим загруженным файлом.

## Обновление

<!-- coverage:update -->

Прочитайте примечания к релизу, выполните `./backup.sh` и перенесите архив вне сервера. Задайте в `VIKUNJA_VERSION` точный проверенный Docker-тег:

```bash
docker compose pull
docker compose up -d --wait --wait-timeout 300
docker compose logs --tail=100 vikunja
```

Не используйте `latest`. Миграции выполняются при запуске. PostgreSQL закреплена отдельно в Compose; до смены версии изучите её процедуру обновления.

## Откат

<!-- coverage:rollback -->

Не запускайте старое приложение на базе после миграций нового. Оставьте PostgreSQL работающей, остановите Vikunja, верните прежнюю точную версию и исходный секрет в `.env`, затем пересоздайте контейнер без запуска:

```bash
docker compose stop vikunja
# Сейчас верните прежние VIKUNJA_VERSION и VIKUNJA_SECRET в .env.
docker compose pull vikunja
docker compose create vikunja
./restore.sh ./backups/vikunja-BEFORE-UPDATE.tar
curl --fail http://127.0.0.1:3456/health
```

Страховочная копия работает с остановленным контейнером, не запуская старое приложение на мигрированных данных. Не понижайте PostgreSQL на существующем физическом каталоге. Если версия БД менялась, восстановите SQL в чистый совместимый том и сохраните прежний до проверки результата.

## Остановка и удаление

<!-- coverage:removal -->

`docker compose down` удаляет контейнеры, сохраняя оба тома. После проверки копии вне сервера `docker compose down --volumes` безвозвратно удалит задачи, аккаунты, настройки и вложения. Удаление каталога рецепта уничтожит и локальные копии; заранее сохраните защищённый экземпляр в другом месте.
