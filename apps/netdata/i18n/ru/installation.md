# Установка Netdata

<!-- coverage:installation -->
## Подготовка Linux-сервера

Нужны Docker Engine и Docker Compose от 2.24 на поддерживаемом Ubuntu или Debian. Команды рассчитаны на Ubuntu 22.04/24.04/26.04 и Debian 12/13; запуск проверен на одном Linux-хосте amd64, а не на каждом дистрибутиве. Установите Docker по официальному руководству для [Ubuntu](https://docs.docker.com/engine/install/ubuntu/) или [Debian](https://docs.docker.com/engine/install/debian/). Проверьте:

```bash
docker version
docker compose version
```

Администраторы Docker могут управлять хостом. Рецепт читает его метрики и разделяет PID-пространство; запускайте его только на системе, которую вправе мониторить. Rootless Docker и ограничительные политики хоста могут уменьшать доступность метрик и не проверялись.

Поместите весь рецепт в `/srv/netdata`, включая `config/`, `proxy/` и оба скрипта восстановления. До запуска:

```bash
cd /srv/netdata
umask 077
cp .env.example .env
chmod 600 .env
chmod 644 config/Caddyfile config/netdata.conf
docker run --rm -it caddy:2.11.7-alpine caddy hash-password
```

Интерактивно введите уникальный пароль. Сохраните его в менеджере паролей, а полученный bcrypt-хеш — в значении `NETDATA_AUTH_HASH` в `.env`, внутри одинарных кавычек. Задайте собственные имя пользователя и имя хоста. Шаблонный хеш отклоняется до открытия HTTP шлюзом. Публичные файлы конфигурации не содержат пароля и должны читаться непривилегированным шлюзом.

```bash
docker compose --env-file .env config --quiet
docker compose --env-file .env up -d --wait --wait-timeout 300
docker compose ps
```

## Первый вход и локальная сеть

Откройте `http://127.0.0.1:19999/v3/`, введите имя пользователя шлюза и исходный пароль, затем используйте локальную панель без входа в Netdata Cloud. Дождитесь накопления штатных измерений. Рецепт не подключает агент к Cloud. `/healthz` открыт, но не содержит метрик; `/api/v1/info` и панель требуют пароль.

Для другой машины предпочтительны SSH-туннель или зашифрованный VPN. Не передавайте Basic-аутентификацию по открытому публичному HTTP. Под Docker Desktop метрики относятся к Linux-VM.

<!-- coverage:deployment-vps -->
## VPS

Оставьте порт на loopback и до настройки HTTPS подключитесь по SSH:

```bash
ssh -L 19999:127.0.0.1:19999 user@server
```

В межсетевом экране разрешите только SSH и нужные HTTPS-порты. Не публикуйте внутренний порт агента и не предоставляйте Docker socket. Защитите и шифруйте внешние копии.

<!-- coverage:deployment-domain-https -->
## Домен и HTTPS

Направьте DNS-имя на сервер. Примеры используют `metrics.example.com`: замените его и сохраните аутентификацию шлюза. Внешний прокси должен передавать клиентский Authorization. Проверьте, что анонимный `/api/v1/info` по-прежнему возвращает 401, а запрос с паролем проходит.

<!-- coverage:caddy -->
### Caddy

Используйте `proxy/Caddyfile` с установленным на хосте Caddy. Он завершает HTTPS и передаёт запросы на `127.0.0.1:19999`; внутренний шлюз продолжает проверять пароль.

<!-- coverage:nginx -->
### Nginx

Используйте `proxy/nginx.conf` в существующей TLS-конфигурации. Сначала получите сертификат, замените домен и пути сертификатов, выполните `nginx -t`, затем перезагрузите конфигурацию. Пример сам не получает сертификаты.

<!-- coverage:traefik -->
### Traefik

Подключите `proxy/traefik.yaml` через file provider к существующим `websecure` и resolver `letsencrypt`. Присоедините контейнер Traefik к frontend-сети этого Compose-проекта, обычно `netdata_frontend`. В ней должно разрешаться имя `gateway`. Внутренняя сеть агента остаётся отдельной.

## Настройки и постоянные данные

| Настройка | Значение |
| --- | --- |
| `NETDATA_VERSION` | Числовая версия Agent; Compose добавляет официальный префикс тега `v`. |
| `NETDATA_PORT` | HTTP-порт шлюза на loopback, по умолчанию 19999. |
| `NETDATA_HOSTNAME` | Имя хоста в агенте; выберите понятное уникальное имя. |
| `NETDATA_AUTH_USER` | Имя пользователя шлюза. |
| `NETDATA_AUTH_HASH` | Bcrypt-хеш пароля в одинарных кавычках. Его замена меняет доступ, сохраняя идентификатор агента. |
| `TZ` | Часовой пояс контейнера, по умолчанию `Etc/UTC`. |

`config/netdata.conf` настраивает агент, `config/Caddyfile` — парольный шлюз. В контейнерах они read-only; редактируйте их на хосте и пересоздавайте соответствующий сервис. Остальные стандартные настройки поставляет исходный образ; дополнительные файлы сборщиков и оповещений требуют явных монтирований и проверки.

Том проекта `netdata-lib` хранит `/var/lib/netdata`, включая идентификатор и API-ключи. `netdata-cache` хранит `/var/cache/netdata`, включая историю dbengine и метаданные SQLite. Для полного восстановления нужны оба тома. Монтирования файловой системы хоста — источники метрик; скрипты backup никогда их не архивируют.

<!-- coverage:backup -->
## Резервная копия

```bash
bash backup.sh
```

Скрипт ненадолго останавливает шлюз и агент, архивирует оба тома, конфигурацию, `.env` и Compose в один закрытый архив в `backups/`. Он запускает только те сервисы, которые работали до копирования; остановленная установка остаётся остановленной. Права архива — 600, каталога копий — 700. Храните зашифрованную копию на другом сервере: локальный архив не защищает от потери хоста.

<!-- coverage:restore -->
## Восстановление — заменяет идентификатор и историю

Используйте доверенный архив и совпадающую версию Agent. Сохраните текущую установку перед продолжением:

```bash
bash restore.sh -y backups/netdata-YYYYMMDDTHHMMSS-PID.tar.gz
docker compose ps
```

Скрипт проверяет архив до изменения данных, создаёт страховочную копию, заменяет оба тома и ждёт healthcheck. Текущие конфигурация, хеш пароля и версии образов остаются активными. Если потеряны и файлы установки, сначала извлеките и проверьте `configuration.env`, `compose.yaml` и `config/` из собственного архива, восстановите `.env` с правами 600, публичные файлы конфигурации — 644. Не выполняйте `source` для недоверенного архивного environment-файла. Затем восстановите данные.

<!-- coverage:update -->
## Обновление

Прочитайте [release notes](https://github.com/netdata/netdata/releases) и сделайте внешнюю копию. Измените `NETDATA_VERSION` на проверенную числовую версию, затем:

```bash
docker compose pull
docker compose up -d --wait --wait-timeout 300
docker compose logs --tail 100 netdata gateway
```

Версию Caddy в Compose проверяйте отдельно. После изменения любого образа проверьте авторизованные графики и отказ анонимным запросам. Один успешный healthcheck не доказывает сохранность истории.

<!-- coverage:rollback -->
## Откат

Сохраните архив и файлы рецепта до обновления. Остановите обновлённые сервисы, верните проверенные старые Compose/конфигурацию и числовую версию Agent, скачайте закреплённые образы, затем выполните `restore.sh -y` с архивом до обновления. Не подключайте старый Agent к потенциально мигрировавшей новой базе. После отката проверьте исходный идентификатор агента и исторический интервал.

<!-- coverage:removal -->
## Остановка и удаление

`docker compose down` останавливает установку, сохраняя оба тома. `docker compose down --volumes` безвозвратно удаляет локальные идентификатор и историю. Сначала сохраните и проверьте внешнюю копию. `.env`, конфигурацию и архивы удаляйте отдельно только при намерении стереть их. Не удаляйте каталоги хоста, которые рецепт читает для мониторинга.
